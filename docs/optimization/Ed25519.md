# Portable Ed25519 implementation record

This document records LiberaCrypt's pure-mode Ed25519 implementation and the
reasoning behind its arithmetic, scalar-multiplication, encoding, and validation
choices. The public API is exposed through `DigitalSignature.h`; all field,
point, and scalar helpers remain internal.

## Scope and encoding

The implementation follows RFC 8032 Ed25519, not Ed25519ctx or Ed25519ph.

- Private key: a 32-byte seed.
- Public key: the canonical 32-byte compressed Edwards point.
- Signature: the canonical 32-byte compressed `R` followed by the 32-byte
  little-endian scalar `S`.
- Hash: SHA-512 as fixed by Ed25519. No hash selector is accepted.

Key generation obtains the private seed from the operating-system entropy
boundary. Public derivation and signing are deterministic for a supplied seed
and message.

## Portable field representation

The field is `p = 2^255 - 19`. A field element uses sixteen little-endian
radix-2^16 limbs stored in `uint32_t`. Schoolbook products fit in 31 `uint64_t`
coefficients: each coefficient sums at most sixteen products of two 16-bit
limbs. High coefficients are folded with `2^256 = 38 (mod p)`, followed by a
fixed number of carry passes and a masked conditional subtraction of `p`.

This representation deliberately avoids:

- `unsigned __int128` and compiler-specific wide-integer extensions;
- architecture-specific intrinsics or assembly;
- variable-length arrays;
- unaligned or aliasing-sensitive word loads;
- native-endian casts; and
- signed shifts or signed-overflow assumptions.

It is the same portability-oriented radix and reduction identity used by the
X25519 backend, while Ed25519 retains its own Edwards-coordinate and strict
encoding rules.

Inversion and square-root candidates use fixed public exponents. Point decoding
accepts only canonical `y < p`, recovers `x`, rejects a non-square, and rejects
the non-canonical encoding whose recovered `x` is zero but whose sign bit is one.

## Extended-coordinate point operations

Points are represented as extended Edwards coordinates `(X:Y:Z:T)` satisfying
`x = X/Z`, `y = Y/Z`, and `T = XY/Z`. Addition and doubling use the complete
formulas for the `a = -1` twisted Edwards curve. Unlike a direct affine
translation, scalar multiplication therefore performs no per-step inversion
and needs no exceptional-case branch for identity, equal, or opposite points.

The reference-shaped baseline would process one scalar bit at a time with one
doubling and one conditional addition, requiring as many as 256 additions. The
implemented four-bit window precomputes the sixteen multiples `0P` through
`15P`, then processes 64 windows. Every window executes four doublings, scans
all sixteen entries with masks, and performs one addition, including zero and
leading windows.

The result is 64 window additions plus 15 precomputation additions rather than
up to 256 bit-conditioned additions. More importantly for private operations,
the loop count, point-operation count, and table addresses do not depend on the
scalar digits. The sixteen-entry table occupies about 4 KiB, a deliberate limit
chosen to remain reasonable on legacy small-stack targets. A larger fixed-base
table should be introduced only with same-target benchmark evidence.

This is described as a fixed source-level schedule. ISO C cannot guarantee
identical instruction or arithmetic latency on every compiler and processor,
and this record does not claim resistance to power, EM, speculative, fault, or
compiler-introduced side channels.

## Scalar arithmetic

SHA-512 outputs are reduced modulo
`L = 2^252 + 27742317777372353535851937790883648493` by a fixed-count binary
reduction over eight 32-bit limbs. Each input bit shifts the bounded remainder
and performs a masked conditional subtraction of `L`.

The signing equation `S = r + k a (mod L)` uses portable 32-by-32-bit
schoolbook multiplication into sixteen 32-bit limbs, fixed-count carry
propagation, and the same 512-bit reduction. Secret expanded scalars and all
temporary digests, reduced scalars, point tables, and coordinates are explicitly
erased after use.

## Strict verification policy

Verification applies the following checks before the signature equation:

1. the public key and `R` must be canonical Edwards encodings;
2. `S` must be strictly less than `L`;
3. the public key must not be the identity; and
4. multiplying the public key by `L` must produce the identity, proving that it
   has no non-trivial cofactor component.

With that prime-order public-key policy, verification checks the direct RFC 8032
equation `[S]B = R + [k]A`; it does not use a permissive cofactored or ZIP-215
acceptance rule.

## Validation evidence

The focused tests include:

- the first three pure Ed25519 known-answer vectors from RFC 8032;
- generated-key public derivation, deterministic repeat signing, and
  empty/non-empty message round trips;
- tampered signatures;
- `S = L`, non-canonical public-point and `R` encodings, and the identity public
  key;
- invalid identifiers, lengths, null pointers, undersized outputs, and
  overlapping output/input ranges;
- strict GCC C11 warning builds with conversion and aliasing diagnostics;
- AddressSanitizer and UndefinedBehaviorSanitizer runs; and
- 100 deterministic seeds and varying messages checked bidirectionally against
  OpenSSL 3.0.13, including exact public-key and deterministic signature bytes.

OpenSSL is a development oracle only and is not a build or runtime dependency.
The normal CI and focused ECC workflow build the public tests on Ubuntu, macOS,
and Windows; the focused workflow also runs the Ed25519 tests under ASan/UBSan
on Ubuntu.

No absolute throughput claim is recorded yet. The window change has a clear
operation-count advantage over bit-wise conditional addition, but a reproducible
multi-platform benchmark is required before publishing timing ratios or choosing
a larger table.
